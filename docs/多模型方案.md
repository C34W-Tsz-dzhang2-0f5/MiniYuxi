# MiniYuxi 多模型 AI 助手 · 产品方案与落地说明

> 参考 WorkBuddy「统一工作台 + 模型可切换」的产品形态，落地到 MiniYuxi 技术栈。
> 本方案已实际跑通：后端 `core/model_hub.py` + `api.py` 的 `/api/models/*` 路由；
> 前端 `web/wb_workbench.js` + `web/index.html` 的模型中心、对话区路由条、对比渲染、模型任务 Tab。

## 1. 产品定位、目标用户与核心使用场景

### 1.1 定位
MiniYuxi 是面向企业知识工作者（HR / 法务 / 运营）的智能工作台。**多模型助手**在既有的
「对话 + 知识库 + 工具」能力之上，内置一个**模型路由中枢（Model Hub）**：一处接入多家大模型
供应商，按任务自动选优、或手动指定、或并行对比并合并，让非技术用户也能「用最合适当前问题的模型」。

### 1.2 目标用户
| 用户 | 诉求 | 多模型带来的价值 |
|------|------|------------------|
| HR / 法务 | 劳动法制度问答零幻觉、口径稳 | 自动路由到中文强的模型；重要决策前多模型交叉验证 |
| 开发者 / 数据分析 | 代码、脚本、SQL | 自动路由到代码/推理强的模型 |
| 运营 / 管理层 | 总结、文案、汇报 | 经济档控成本；对比档交叉验证避免单一模型偏见 |
| 团队负责人 | 成本可控、可审计 | 每次调用落库，右侧「模型任务」回看用量与延迟 |

### 1.3 核心场景
1. **制度/法务问答**：识别为 `hr-policy`，默认均衡档路由到中文通用强模型。
2. **代码 / 脚本**：识别为 `code`，路由到代码/推理强模型（DeepSeek / GLM / MiMo）。
3. **深度推理**：`reasoning`，强力档优先旗舰推理模型。
4. **总结提炼**：`summary`，平衡档长上下文模型。
5. **多模型交叉验证**（重要决策前）：勾选 2~N 个模型并行回答，裁判模型合并「共识 + 分歧 + 建议」。
6. **成本敏感高频任务**：`translate` 等，经济档优先便宜快模型。

### 2.1 三个关键区域
- **对话区**：消息流 + 对比结果并排卡片组（多列）+ 合并结论区。

- **会话与任务管理区（右侧 Tab）**：在原有「概览 / 产物」之外新增「模型任务」，展示统计与历史。

## 3. 多模型的接入、手动切换与自动调度策略

### 3.1 一处接入（统一协议）
所有供应商走 **OpenAI 兼容** `/chat/completions`。新增厂商只需在 `model_hub.PROVIDERS` /
`MODELS` 追加一条，调用方无需改动。已接入：

| 供应商 | base_url | 代表模型 |
|--------|----------|----------|
| 硅基流动 SiliconFlow | api.siliconflow.cn/v1 | Qwen2.5-72B/7B、DeepSeek-V3/R1、GLM-4-9B |
| DeepSeek 官方 | api.deepseek.com/v1 | deepseek-chat / deepseek-reasoner |
| 小米 MiMo | api.xiaomimimo.com/v1 | MiMo-v2.5-Pro / v2.5 / v2-flash |
| 火山方舟 Ark | ark.cn-beijing.volces.com/api/v3 | 豆包 Seed 2.1 Pro / 1.6 / 1.6 Lite |
| 智谱 GLM | open.bigmodel.cn/api/paas/v4 | GLM-4.6 / 4.5-Air / 4.5-Flash |
| 自定义 / 离线兜底 | 可配 | 任意 OpenAI 兼容 / 无 Key 抽取式兜底 |

> Key 优先级：**库配置（`model_providers` 表，界面可填）> 环境变量 > 默认值**。硅基流动未显式配置时
> 沿用全局 `LLM_API_KEY` 向后兼容。

### 3.2 手动切换
模型中心点击某模型卡片 → 设为「指定模型」；路由条切到「指定模型」模式即固定走该模型。

### 3.3 自动调度
1. **规则识别任务类型**：零成本关键词匹配（代码 / 推理 / agent / 制度 / 总结 / 翻译 / 创意 / 通用），
   返回类型 + 置信度（可解释，不额外消耗 token）。
2. **按策略档打分选优**：在「已配置 Key 的可用模型」中，依据
   `能力匹配（主） + 档位倾向 + 成本惩罚 + 长上下文加分` 打分：
   - **经济**：越轻量越加分、成本权重翻倍 → 便宜模型能赢旗舰；
   - **强力**：越旗舰越加分、成本几乎不计 → 旗舰优先；
   - **均衡**：贴近任务推荐档位。
3. 返回含「理由 + 候选 Top5」便于前端解释。

### 3.4 多模型并行对比 + 结果合并
- **并行**：`ThreadPoolExecutor` 并发打多个模型，返回结构化结果（延迟 / token / 成本 / 正文）。
- **合并**：用一个**裁判模型**（默认可用且 tier 最高的模型）把多路答案汇成：
  `## 共识`（一致事实）/ `## 分歧`（逐模型标注）/ `## 最终建议`（唯一可执行结论）。

### 3.5 可观测
每次调用落 `model_tasks` 表 + usage 埋点；右侧「模型任务」Tab 回看统计与逐条结果。

## 4. 主要功能模块与关键交互流程

### 4.1 功能模块
| 模块 | 入口 | 能力 |
|------|------|------|
| 模型中心 | 顶部「模型切换」 | 供应商状态、三档策略、模型卡片（点选指定 / 勾选对比） |
| 路由条 | 对话区 composer 上方 | 四模式切换 + 模式摘要 + 模型中心入口 |
| 单模型对话 | 路由条「工作台 / 自动 / 指定」 | 走 `/api/wb/chat` 或 `/api/models/chat` |
| 对比对话 | 路由条「多模型对比」 | 走 `/api/models/compare(merge)` → 并排卡片 + 合并结论 |
| 任务管理 | 右侧「模型任务」Tab | 统计 + 历史（点击展开 result） |
| 供应商配置 | 后端 `/api/models/providers`（agent.run） | 落库 Key / base_url / 启用 |

### 4.2 关键交互流程
**A. 多模型对比（交叉验证）**
```
用户打开[模型中心] → 勾选 ≥2 个模型 → [应用] 
→ 路由条切到[多模型对比] → 输入问题发送 
→ 后端并发调用各模型 → 渲染并排卡片(延迟/token/成本/正文) 
→ 裁判模型合并「共识/分歧/建议」 → 落 model_tasks
```
**B. 自动路由（省心）**
```
用户保持[自动路由]（默认均衡档）→ 输入问题发送 
→ 后端识别任务类型 + 打分选优 → 返回最优模型回答 + 路由理由 
→ 落 model_tasks
```
**C. 手动指定（可控）**
```
用户[模型中心]点卡片设为指定模型 → 路由条切[指定模型] → 发送 
→ 固定走该模型
```

### 4.3 API 清单
| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/models/catalog` | 供应商 + 模型目录 + 策略 + 默认模型 |
| POST | `/api/models/route` | 给定问题返回路由建议（类型/档位/候选） |
| POST | `/api/models/chat` | 自动或指定模型单轮对话（记录任务） |
| POST | `/api/models/compare` | 多模型并行对比（可 merge） |
| GET | `/api/models/tasks` | 任务列表 + 统计 |
| POST | `/api/models/providers` | 配置供应商 Key（agent.run） |
| POST | `/api/models/test` | 单模型连通性探针 |

## 5. 技术约束与红线
- **不新增外部依赖**（复用 `requests`）；**不改动三指纹文件**（`selftest.py` / `core/db.py` / `core/agent.py`）。
- 建表一律 `CREATE TABLE IF NOT EXISTS`；`db.connect()` 返回线程级单例连接，本模块禁止 `close` 它。
- 前端新增样式以 `mx-` 前缀内联于 `index.html`，避免与 `wb_workbench.css` 同名类冲突。
- 默认对话模式仍为「工作台」（保留专家 / 技能 / 连接器 / 文件），多模型模式为叠加能力，互不破坏。
