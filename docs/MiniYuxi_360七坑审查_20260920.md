## 一句话结论

MiniYuxi 在 360 七坑里**没有踩致命坑（无 🔴）**。**最值得记的是它亲身踩过、又闭环修复了「坑3 一键生成」**——AI 改码不验证 → `saveMsgs` 未定义导致「无法对话」回归，后建独立验证闭环补齐。而「坑1 贪大 / 坑2 裸奔 / 坑5 副驾驶 / 坑6 自生自灭」靠"技术轻量 + RAG 知识库 + 40+ Skill 注册表 + AI 原生流程编排"基本规避。真正待补的是两处 🟡：**验证脚本未接 CI 卡点（坑3 复发风险）**、**根目录文件散落（坑4 轻度）**，以及**组织机制是否同步（坑7）**。

## 逐项分析

### 坑1 贪大坑 —— 🟢 低（附 🟡 提示）
- **现状**：定位"轻量 HR 智能体平台（自研原型）"，技术上确实轻——单 Python 进程、内存 65–70MB、零外部服务（SQLite + sqlite-vec + FTS5，无 Milvus/Docker）。核心闭环（对话+引用溯源、Agent S1→S19 跑通、selftest 20/20）已验证，且有"离线兜底"可无 Key 完整验收，符合"小步快跑、先跑通闭环"。
- **🟡 提示**：功能面随 40+ skills 扩张较广（多租户/权限/知识库/招聘/简历/劳动纠纷/公文/合规），需确认 selftest 20/20 是否覆盖专业 skills，避免"核心轻、边缘重"。
- **改进**：把专业 skills（劳动法、公文、简历）跑通也纳入 selftest/集成测试，而非只验核心层。

### 坑2 裸奔坑 —— 🟢 低（附 🟡 提示）
- **现状**：**最关键的"专业大脑"已装**。RAG 知识库（`core/rag.py`）+ 引用溯源（/api/chat 返回 `mode=offline` 原文片段、带溯源）+ 40+ 专业 Skill，其中 `legal_norm_validity_check`（法条效力核验）、`labor_dispute_workflow`、`hr_compliance_toolkit` 直接对应"法务/HR 专业规则库"。这恰好是 360 解法的"建知识库→搭智能体→固化 Skill"三步。
- **🟡 提示**：架构设计上要求引用，但需确认**劳动法条类高风险输出是否硬约束走知识库/规则库**，而非 LLM 自由生成（阿长铁律：法条引用必核验，不凭印象）。
- **改进**：在 `legal_*`/`labor_*` 链路加"无引用不出文"的硬闸门，未命中知识库则拒绝自由生成法条。

### 坑3 一键生成坑 —— 🟢 已修复（🟡 复发风险）
- **现状 = 最相关**：9-16 亲身踩中——AI 生成的 `wb_workbench.js` 中 `saveMsgs/loadMsgs/saveConvos` **只调用未定义**（U2 函数块半落地），导致消息不渲染、"无法对话"。这正是 360 说的"生成快、验证没跟上，人成瓶颈"。
- **已闭环修复**：同一天补建独立验证闭环——`_smoke_routes.py`(40 路由断言)、`_scan_undef.py`(被调未定义符号静态扫描)、`_visual_check.py`(Playwright 真实浏览器四视口)、`_verify_chat_fix.py`(10/10)、`_verify_model_fallback.py`(4/4)。**这正是 360 解法的"独立子代理审查、避免主代理自我盲区"**，与阿里 ocr「确定性工程 + Agent 混合」同构。
- **🟡 复发风险**：这些验证脚本**散在根目录、未接 CI / pre-commit 卡点**，下次"改完不验"仍可能绕过。
- **改进**：把 `_scan_undef.py` + `_smoke_routes.py` 接成 PR 前强制卡点（GitHub Actions / pre-commit hook），未过则阻断合并。

### 坑4 孤岛坑 —— 🟢 低（🟡 轻度）
- **现状**：知识资产已集中——`core/skills.py` + `skills_catalog.py` 统一注册表、`core/rag.py` 知识库、`workflows/*.yaml` 流程定义，团队/多模块可共享同一套底座，非"每人各玩各的"。
- **🟡 轻度**：根目录文件组织混乱——验证脚本(`_*.py`)、截图(`jd_run.png`/`snap_*.png`/`ui_v2_*.png`)、备份(`index.html.bak_*`)、日志(`smoke_*.log`/`verify_out.txt`)、临时文本(`*.txt`)混在仓库根，知识未完全结构化。
- **改进**：验证脚本归 `tests/` 或 `scripts/`，截图/日志/bak 清理或归档到 `docs/_shots`、`docs/_archive`，统一落 `docs/`，保持根目录只放源码与说明。

### 坑5 副驾驶坑 —— 🟢 低
- **现状**：MiniYuxi 定位即"AI 原生重构 HR 工作流"，不是"AI 帮我更快写码"。`core/agent.py` 招聘 19 阶段状态机 + HITL 闸门，人只做判断与决策（如 HITL 中断审批），整条链路重建而非局部提速。
- **改进**：无，保持。

### 坑6 自生自灭坑 —— 🟢 低
- **现状**：踩坑经验已固化成 Skill（仓库内 `skills/` 40+，外部 workbuddy 侧 `miniyuxi-module-scaffold`/`github-sandbox-fetch`），不依赖个人脑中经验，新人/其他智能体可直接调用。
- **改进**：把"ocr 安装+预检""前端独立验证闭环"也补进 `miniyuxi-module-scaffold`，形成可复用资产。

### 坑7 惯性坑 —— 🟡 中
- **现状**：阿长个人与项目打法在变（用 AI 原生方式处理李俊华案/张颜案、HR 流程），但车务通公司作为组织，其 HR/案件协作、考核、审批机制是否因 MiniYuxi 而同步调整，仓库与对话中均无证据。
- **改进**：若 MiniYuxi 推向车务通团队，需同步定"谁用、怎么验收、考核什么"的组织机制，否则易成"速度更快的旧流程"。
