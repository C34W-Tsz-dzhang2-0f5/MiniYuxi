# 从智谱 ZCode 逆向复制到 MiniYuxi：研究报告（2026-09-24）

> 源文章：[推荐一个智谱开源的企业级 AI Agent 智能体开源项目](https://mp.weixin.qq.com/s/yoNA0M1ZCef4wUinpgWI2w)
> 研究对象：**ZCode**（智谱 Z.ai 开源，2026-09-20，Apache-2.0，基于 GLM-5.3，约 84 万行 TS）
> 代码：https://github.com/zai-org/ZCode
> 任务：阿长指定 4 个维度（企业知识库检索 / 子智能体 / 多端协作 / Command）深挖，挑值得逆向复制的落进 MiniYuxi
> 方法论：文章全文 + GitHub README + MiniYuxi 现有源码（`web/wb_workbench.js` 的 `openKbModal` / `openAssistantModal` / `/` 触发逻辑）三路对照

---

## 一句话结论

**4 项里 2 项值得马上抄（Command、企业知识库检索），1 项分阶段抄（子智能体），1 项不建议照抄要改轻量版（多端协作）。** ZCode 本质是「AI 编程工作台」，你挑的这 4 项恰好是它身上**不绑行业的通用能力层**——但要按 MiniYuxi「本地 Tauri + HR 场景 + 小团队」的体格裁剪，**不能照搬它的重型基础设施**。

---

## ⚠️ 落地前先把 3 个风险说清

1. **🟡 ZCode 是编程工作台，很多能力是「代码中心」的**：它的知识库是「代码库架构导读」、子智能体在「读代码/改代码」上下文里跑、远程开发是 SSH/WSL。照搬前必须做「HR 语义平移」，否则会抄成四不像。
2. **🟡 MiniYuxi 是本地 Tauri 应用，没有公网服务器**：ZCode 的多端协作依赖远端 server + 微信/飞书 Bot（都要公网 + 资质 + 合规）。HR 数据敏感，**绝不能直接走微信 Bot 通道**，隐私敞口大。
3. **🟢 但有两个能力 MiniYuxi 已经半只脚踩进去了**：`/api/kb/*`（知识库弹窗已有列表/上传/提问）、`/api/subagent`（子 Agent 编排已有，生成器/评判器分离）——所以抄的边际成本比从零低得多。

## 逐项深拆

### ① Command —— `/` 斜杠指令（P0，最值得抄，成本最低）

**ZCode 怎么做**
- Command = 把团队反复用的提示词（代码审查 / 提交说明 / 发布检查 / 文件解释）沉淀成命令，在输入框用 `/` 快速调用。
- 两类：内置 Agent 能力快捷入口 + **用户保存的常用提示词模板**。
- 围绕 Agent 工作流设计，让自研 Agent 稳定执行固定流程。

**为什么好**
- 把"重复提示词"变成一键资产，**降低 HR 日常操作的Prompt 成本**（例如"生成离职面谈提纲"每次都要写一遍）。
- 与 MiniYuxi 已有的 `/` 触发机制**天然契合**，几乎零架构改动。

**MiniYuxi 现状**
- `wb_workbench.js` 的 input 监听：键入 `/` → `openSkillDrawer()`（只能调技能）。
- 没有"用户保存提示词模板"这一层。

**逆向方案（落地路径）**
1. 把 `/` 抽屉从"只列技能"扩成 **两类**：`技能`（现有）+ `指令模板`（新增）。
2. 新增 `POST /api/commands`（或 localStorage）存用户模板：`{id, name, prompt, scope}`。
3. 输入框加「把当前这条消息存为指令」的按钮。
4. 预置几个 HR 内置命令：`/生成离职面谈提纲`、`/核算本月社保`、`/起草录用通知`、`/试用期评估`、`/制度问答`（直接走资料库）。
5. 调用时把模板正文回填进输入框（复用现有 `@`/`/` 回填逻辑）。

**优先级**：P0。**收益/成本比最高**，建议第一波先做。

---

### ② 企业知识库检索 —— 资料库升级为「带出处的制度地图」（P0，值得抄，部分已有）

**ZCode 怎么做**
- 定位是「代码库架构导读」，**不是产品文档站**：读一遍代码库 → 整理成可查文档。
- 目录优先覆盖：项目身份 / 主执行链路 / 核心模块 / 跨端边界 / 数据与状态流 / 配置边界 / 扩展点 / 风险点。
- **所有结论都带源码位置，可点击跳回对应文件**（这是它的灵魂——可溯源）。

**为什么好**
- 核心价值不是"能问答"，而是**答案可溯源 + 结构化导读**，避免 AI 一本正经胡说。
- 对 HR 场景极度适配：制度/流程/政策问答最怕"张冠李戴"，**出处引用是刚需**。

**MiniYuxi 现状**
- `openKbModal()` 已有：`/api/kb/docs`（文档列表）、`/api/kb/upload`（上传）、`/api/kb/ask`（提问）。
- **缺两块**：(a) 答案的**出处引用/可点击跳转**；(b) 上传后的**结构化「制度地图」导读**（目前是平铺文档列表）。

**逆向方案（落地路径）**
1. **出处引用**（对齐 ZCode 灵魂）：`/api/kb/ask` 返回时附带命中的 chunk + 来源文档名 + 段落锚点，前端渲染成可点的引用角标。
2. **制度地图**（对齐"架构导读"）：按 HR 域（招聘 / 薪酬 / 社保 / 离职 / 绩效 / 合同 / 合规）给文档打标签，首页给一张"按场景找制度"的导读卡，而非平铺列表。
3. **自动切片+向量化**：上传即 `POST /api/kb/index` 自动 chunk+embed（若后端还没做，这是前置）。
4. **只读子智能体挂钩**：把"制度问答"做成 Explore 类只读 Agent（见③），只查不写，安全。

**优先级**：P0。与 Command 同波，因为两者共享"资料库"底座。

**⚠️ 风险**：RAG 质量取决于切片与 embedding；HR 文档常有表格/扫描件，需先做"表格可解析 + OCR"预处理，否则出处会乱指。

### ③ 子智能体 —— 用户级自定义 + 只读 Explore（P1，分阶段抄，不要一步到位）

**ZCode 怎么做**
- 主 Agent 在**独立上下文**派生子 Agent，完成后**结果汇总回主对话**。
- 内置 `general-purpose`（通用）+ `Explore`（只读调研）。
- 现在可在设置里创建**用户级子智能体**（自定义角色）。

**为什么好**
- 把"长任务"拆给并行子 Agent，主会话不被污染，适合复杂多步 HR 流程（如"同时核社保、查合同、对考勤"）。
- 只读 Explore 是关键安全设计：调研类任务不让它动文件。

**MiniYuxi 现状**
- `/api/subagent` 已存在，且是**生成器/评判器（generator/critic）分离**架构（`openAssistantModal` 注释确认）。
- 但：没有用户级自定义、没有只读模式开关、没有"从主会话派发 + 回汇"的 UI 编排。

**逆向方案（落地路径，分阶段）**
- **阶段 A（先做）**：加一个**内置只读 Explore 子 Agent**，专做"资料库/制度检索"，只查不写，前端一键委派，结果以卡片汇回主会话。成本最低、收益最稳，且契合 HR"先查后办"的纪律。
- **阶段 B（后做）**：设置面板支持**用户级子智能体**（名字 + 角色 + system prompt + 工具范围 + 只读开关），存 localStorage / 后端。
- **阶段 C（看需求）**：显式"主→子"派发编排 UI（`@子智能体` 或 `/` 调用），结果聚合。
- **不要照搬**：ZCode 的子 Agent 在"读代码/改代码"上下文跑，MiniYuxi 要平移成"只读调研 / 流程办理"两类，且**默认只读**，避免子 Agent 误改 HR 数据。

**优先级**：P1。建议放在 Command + 知识库之后，因为前两者能立刻用、子智能体要动后端编排。

**⚠️ 风险**：多 Agent 并发会放大 token 成本与上下文污染；HR 场景下"子 Agent 误写"代价高，**只读默认 + 显式授权写**是硬约束。

---

### ④ 多端协作 —— 不照抄，改"局域网只读 Web 视图"轻量版（P2，暂缓）

**ZCode 怎么做**
- **手机 Remote**：扫码把桌面窗口临时开放给手机，手机查看/切换工作区、任务、会话，发指令（手机不同步代码、不建运行环境，指令由桌面机执行）。
- **Bot Channel**：微信/飞书 Bot 接入，从聊天里打开工作区、看进度、发指令。
- 底层依赖：公网 server + WebSocket + 鉴权（`ZCODE_SERVER_AUTH_TOKEN`）。

**为什么"不全抄"**
- ZCode 的多端是**公网产品**能力，要服务器 + 资质 + 合规。MiniYuxi 是**本地 Tauri 工具**，没有服务器底座。
- **微信/飞书 Bot 通道对 HR 数据极不友好**：员工薪酬、合同、仲裁案卷都是敏感个人信息，走公网 Bot = 隐私敞口 + 合规雷区（个保法/数据安全法）。**这条坚决不抄。**
- SSH/WSL 远程开发是编程专属，与 HR 无关。

**逆向方案（轻量版，仅当真有需求时）**
- **局域网只读 Web 视图（推荐替代）**：MiniYuxi 已经 `127.0.0.1:<port>` 起 Web 服务，把它**绑到局域网 + 简单 token 鉴权**，同 WiFi 下用手机浏览器打开**只读**任务视图、可发指令。成本远低于 ZCode 的远程方案，且不触公网合规红线。
- **不要做**：微信/飞书 Bot 接 HR 数据；公网穿透；手机端"同步代码/建运行环境"。
- 真要"手机推进任务"，走**企业微信自建应用 + 内网**也比公网 Bot 安全，但仍是 P2 之后再说。

**优先级**：P2（暂缓）。除非阿长明确要"出差用手机看进度"，否则不投入。

## 综合落地顺序（给阿长的建议）

| 波次 | 内容 | 工作量 | 收益 |
|---|---|---|---|
| **第一波（P0）** | Command 扩展（`/` 加指令模板）+ 资料库出处引用 + 制度地图 | 小（扩展现有） | 🟢 高：HR 日常提效立竿见影 |
| **第二波（P1）** | 子智能体：内置只读 Explore + 用户级自定义 + 回汇 UI | 中（动后端编排） | 🟡 中：复杂多步流程提速 |
| **第三波（P2，可选）** | 局域网只读 Web 视图（轻量多端替代） | 中（要绑 LAN+鉴权） | 🟡 中：仅当手机跟进需求明确 |

**明确不建议抄的两处**：① 微信/飞书 Bot Channel（HR 数据合规雷区）；② SSH/WSL 远程开发（编程专属，与 HR 无关）。

## 是否要我动手

本报告是**研究与选型**，未改动任何 MiniYuxi 代码。若阿长认可，建议从**第一波**开刀（Command + 资料库出处引用），这两项都能在现有 `wb_workbench.js` / `/api/kb/*` 上增量做，风险最低、见效最快。你说一声"做第一波"，我就出改造方案 + 落地。
